# RFC 0038: Multi-Agent Evidence Graph

## Status
Draft for implementation.

**Target gate:** G2 (agent-computer interface); promotion authority feeds every gate's evidence discipline
**Owners:** evidence/workbench leads
**Normative language:** MUST/SHOULD/MAY per RFC 2119.
**Normative schemas:** [`../schemas/evidence-graph-node.schema.json`](../schemas/evidence-graph-node.schema.json) and [`../schemas/evidence-graph-edge.schema.json`](../schemas/evidence-graph-edge.schema.json) carry the normative plan §11 content — node kinds, edge types, the §11.4 status lattice, typed `Inconclusive` reasons (INV-008), `validation_basis` (`checked-certificate` vs `trusted-solver`), and parameterization (`checked / cutoff_checked / proved_universal`). [`../schemas/whiteboard-note.schema.json`](../schemas/whiteboard-note.schema.json) carries the plan §11.5 whiteboard note format. This RFC summarizes; the schemas decide.

## Nodes/edges
Typed immutable candidates, claims, failures, proofs, patches, runs, receipts, conflicts, and decisions, connected by the 13 plan §11.3 edge types: `SUPPORTS`, `REFUTES`, `DEPENDS_ON`, `REFINES`, `EXPLAINS`, `REPAIRS`, `INVALIDATES`, `GENERALIZES`, `COUNTEREXAMPLE_TO`, `CHECKED_BY`, `DERIVED_FROM`, `CONFLICTS_WITH`, `SUPERSEDES`. Edges name checker/evidence when applicable; the machine encoding is [`schemas/evidence-graph-edge.schema.json`](../schemas/evidence-graph-edge.schema.json) (nodes: [`schemas/evidence-graph-node.schema.json`](../schemas/evidence-graph-node.schema.json)). The library vocabulary is `crates/continuum-evidence`; the one wire verb that appends an edge is `evidence.link` (plan §10.2, protocol 3.3), and what it may append is decided under "Edges: what a `CHECKED_BY` edge names" below. `whiteboard.compile` (protocol 3.5) appends `SUPPORTS` edges too, but only the ones a note's decisions draw and never a `CHECKED_BY` — D3 makes a check edge the checker's own artifact, and a note author is not that service whatever the note says.

## Authority
Actor capabilities control node creation; status promotion is service-restricted. Confidence is metadata. The status lattice is exactly plan §11.4 (`Proposed, Observed, Sampled, Bounded, Validated, Proved, Refuted, Inconclusive, Superseded` — there is no `draft` status). Only trusted services promote into `Validated` or `Proved`; `Sampled` and `Bounded` promotions name the producing engine's service identity; every `Inconclusive` carries a typed INV-008 reason. Agent votes or confidence never change status.

**Edge creation (D3, decided at protocol 3.3 by bn-3sypm; this section previously covered node creation and status promotion only).** Twelve of the thirteen edge kinds are ordinary assertions and are created under the same actor capability that creates a node. `CHECKED_BY` is not: it is the graph's record that an *independent* check happened, so it is the checker's own artifact and no one else's.

- **The checker is the caller.** A `CHECKED_BY` edge MUST be appended by the service that performed the check, and the edge's `checker` MUST be taken from the admitted capability's actor — never from a request field. There is no wire field that names a checker, for the same reason there is no wire field that names a status: a field a caller can fill is a field a caller can lie in. This is the device `observe.ingest` already uses for `provenance.actor`.
- **A checker is a `service:` actor.** An `agent:`, `human:`, or `ci:` capability MUST NOT be able to append a `CHECKED_BY` edge at all. RFC 0027 P3 says an evidence-status write is "performed by a trusted service identity"; the edge that *records* the check is held to the same scheme, and the refusal is `CapabilityDenied` (RFC 0027 X1: a denial is a unit).
- **No self-certification (INV-004).** A `CHECKED_BY` edge whose checker equals the `from` node's `provenance.actor` MUST be refused. This is the edge-level statement of the same rule `EvidenceGraph::promote` and `evidence.verify` already enforce for promotion, and it is checked *before* anything about the checked artifact is read, because a service checking its own production has established nothing whatever the bytes say.
- **An edge is not a promotion.** Appending a `CHECKED_BY` edge writes no status, mints no promotion witness, and cannot reach the compare-and-set. The two are separate operations on purpose: an edge is evidence *that* a check ran, and what that evidence licenses is a later, separate decision. RFC 0027's "no `evidence` operation writes a status" therefore survives the addition unchanged.
- **Not the daemon's own side effect.** `evidence.verify` MUST NOT silently append a `CHECKED_BY` edge as a by-product of a promotion. A daemon that both promoted and recorded the check would make the record indistinguishable from the promotion it justifies.

## Edges: what a `CHECKED_BY` edge names (RFC 0026 F14)
Four questions this RFC left open blocked INV-004's edge dimension — plan §2 SD-11, "`evidence-graph-edge` requires `checker` on `CHECKED_BY`". They are decided here; `crates/continuum-evidence` carries the library half and the native protocol carries the wire half (`evidence.link`, `@since("3.3")`).

**D1 — the `to`-handle names a `receipt`, and only a `receipt`.** RFC 0026 F14 offered three candidates (`run`, `certificate`, `receipt`) and observed that "there is no node kind for a check". There is one: plan §11.2's `ProofReceipt`, whose format is RFC 0024, is precisely the artifact a checker emits to record that it checked something. The other two are rejected on INV-004's own words — "search code does not check its own strongest claims; certificates cross an independent checker":

- a `run` is search's own output, so an edge pointing at one would let the search machinery be its own check;
- a `certificate` is what *crosses* a checker, not the crossing. It belongs on the edge's `from`, and the canonical sentence is `certificate CHECKED_BY receipt`. An artifact offered *toward* a claim is a `SUPPORTS` edge; the vocabulary already has the word.

So the direction is fixed too: `from` is the checked subject, `to` is the receipt that records the check, and `checker` is the service that produced the receipt. `CheckTargetRule` in `crates/continuum-evidence/src/edge.rs` holds the rule as data and its default is now this decision rather than `Undecided`.

**D2 — `edge_id` is the content identity of what the edge asserts, named through one seam.** Identity is the canonical preimage (ADR-0013); the `ev_` token is a *name for* it, minted in an explicitly labeled non-certified mode, which is why naming is separable at all (`identity::EvidenceNaming`). The wire's naming is the deployment's `ContentIdentifier` seam at `ArtifactClass::Evidence` — the same seam and the same class that names nodes, so one identity kernel names every evidence artifact and `evidence.verify`'s re-derivation discipline extends to edges unchanged. The preimage is domain-separated from a node's by a leading `evidence-graph-edge/v1` tag, which is outside the artifact-handle character class and therefore cannot be a commitment, so no node preimage can spell an edge preimage.

**D3 — edge-creation authority** is the "Authority" section above.

**D4 — a node's wire identity is what the node is *about*.** Two derivations existed and this RFC fixed neither: `continuumd`'s `observe.ingest` derives a node handle from (referenced artifact commitment, capture profile), and `continuum-evidence` derives its content key from the whole record minus status and idempotency key — which includes `provenance`, and therefore the producing actor and the wall-clock capture time. **The daemon's is the wire's.** The reason is this RFC's own sentence: "a replayed write returns the original node identity" is a claim *across processes and across producers*, and an identity that contains a clock cannot support it — two ingests of one trace under one profile would mint two nodes, and convergence would depend on when and by whom the write arrived, which is the write-order resolution plan §11.7 forbids. So:

- a node's wire identity is a function of the artifact it is about and the profile it was captured under, and of nothing else; `provenance` is deliberately outside it, as `status` and `idempotency_key` already are;
- an edge's wire identity is likewise a function of what it asserts — kind, both endpoints, and the checker — and not of who asserted it or when, so a checker's retry converges on one edge;
- `continuum-evidence`'s `EvidenceIdentity` is a **within-graph content key**, not a wire name. It never appears on the wire: `EvidenceNode::to_record` and `EvidenceEdge::to_record` take the handle as a *parameter*, so the library already accepts the wire's names as input rather than deriving them. A library graph joined to the wire supplies handles through `EvidenceNaming`; it does not ask the library to name anything.

## Write and concurrency model
Absorbed from plan §11.7 (SD-06). The graph is append-only; nothing is edited in place. Publication is per-artifact atomic (INV-017). Status promotion is linearized per claim identity as a compare-and-set against the claim's current status: racing promotions cannot regress the lattice, and a lost CAS returns the typed `StatusConflict` error (plan §10.3) — the caller re-reads and retries against the current status. Concurrent contradictory claims materialize a `Conflict` node rather than resolving by write order. Idempotency keys (RFC 0026) make agent retries safe: a replayed write returns the original node identity. The node schema MUST carry `claim_id`, `idempotency_key`, and `service_identity` for this purpose.

Enforcement of this model is a frontier lane: the ratified validation criteria for the plan §24.5 row (writer counts, zero-tolerance bounds, and deterministic conflict artifacts) live in [`research/08`](../research/08-agentic-verification.md), which the register quotes verbatim.

## Queries
Missing obligations, conflicting candidates, proof frontier, repair frontier, semantic duplicates, provenance, and task generation. `crates/continuum-evidence/src/graph.rs` ships the selection-and-traversal layer these are written in and `EvidenceGraph::contradictions` ("conflicting candidates"); the other six are named as not-delivered because they need artifact content the graph does not hold — a proof frontier needs proof obligations, semantic duplicates need semantic equality — and inventing them over handles alone is the empty-success shape `rule errors.unsupported_surface` forbids. Whether they are wire operations at all or library queries over content a later PR supplies is undecided.

## Whiteboard compiler
Converts structured notes to proposed nodes; rejects nonexistent references and status claims without evidence.

**The note format is a schema (W1–W9, decided by bn-2qa0u); the wire is W10–W12, decided by bn-1as8e.** plan §11.5 states seven section headings — `Goal`, `Known facts`, `Candidate invariant`, `Counterexample`, `Unresolved obligation`, `Experiment`, `Decision` — as prose inside a code block, and INV-003 says prose does not decide artifact shape. The input format is therefore [`../schemas/whiteboard-note.schema.json`](../schemas/whiteboard-note.schema.json), and `crates/continuum-evidence/src/whiteboard.rs` is transcribed from it. What §11.5 implies but does not decide is decided here; each answer is a property of the format rather than a check the compiler runs.

- **W1 — one goal, six possibly-empty sections, all twelve members required.** §11.5 opens "for complex invention *tasks*" and spells `Goal` singular, so a note has exactly one goal and a note with two goals is two notes. The other six sections are arrays that MAY be empty but MUST be present: an omitted section and an empty section would otherwise be two spellings of one note, and the compilation is required to be a function of the note's content.
- **W2 — heading decides node kind.** `Goal` → `property` (plan §11.2 `Property` is "a property to be established"); `Known facts` → `assumption`; `Candidate invariant` → `invariant_candidate`; `Counterexample` → `counterexample`; `Unresolved obligation` → `proof_goal` (§11.2 `ProofGoal` is "a goal handed to a proof worker"); `Decision` → `decision` (§11.2 `ReviewDecision`). An author MUST NOT be able to name the kind directly: if it could, the seven headings would be decoration. `Known facts` → `assumption` is the load-bearing one — reading an author's "known fact" as `observed` would be exactly the promotion docs/44 forbids prose from performing.
- **W3 — an experiment is a task proposal, not a node.** docs/44 says "experiments become task proposals" and plan §11.2's twenty node kinds have no task kind, so an `Experiment` entry carries neither a claim identity nor a subject and compiles to a typed proposal returned beside the nodes. Growing the closed node vocabulary to hold one would be a larger act than this RFC is making.
- **W4 — references resolve, subjects do not have to.** An entry's `references` are prior artifacts and MUST each name an artifact the graph holds a node about (docs/44 "references must resolve"). Its `subject` is what the entry is *about* and MUST NOT be required to resolve: an entry whose subject the graph already held could propose nothing new, which is what a whiteboard is for. The references become the compiled node's `provenance.inputs` — derivation, never assertion.
- **W5 — the format has no status member, and the compiler does not read prose.** RFC 0038's "rejects […] status claims without evidence" is met by the absence of a field, not by a filter: a field a producer can fill is a field a producer can lie in (D3), and a scanner for status *words* would make the graph a function of wording. `text` is human commentary, is never parsed, and never enters a node — INV-003: "human text may accompany a machine result, never define it".
- **W6 — a decision cites at least one supporting artifact, and each becomes a `SUPPORTS` edge.** docs/44's "conclusions require supporting edges" is the schema's `minItems: 1` on a decision's `references`, so an unsupported conclusion is unrepresentable rather than refused. Where the graph holds several nodes about one cited artifact, one edge is drawn from each: choosing between them is a semantic judgement the compiler cannot make, and citing an artifact is the only way the format lets an author name support.
- **W7 — `SUPPORTS` is the only edge kind the compiler emits.** A `Counterexample` entry emits no `REFUTES` and no `COUNTEREXAMPLE_TO`: whether a counterexample refutes a candidate is a judgement over artifact content the evidence graph does not hold, and asserting it from a section heading is the empty-success shape `rule errors.unsupported_surface` forbids. A `CHECKED_BY` edge is unreachable by construction — D3 makes it the checker's own artifact, and a note author is not that service whatever the note says.
- **W8 — refusal is whole-note, and nothing is ever dropped.** The compiler returns a complete compilation or a typed refusal naming the offending section and line; it MUST NOT emit a partial proposal set (INV-017's per-artifact atomicity read at the note's granularity). It has no merge, dedup, or reconciliation step either, which is how docs/44's "unresolved contradictions remain visible" is met: two entries in tension are two proposals, and resolving one by authoring order is precisely what plan §11.7 forbids.
- **W9 — the note is provisional and is not a new artifact class.** A note is not one of plan §4.4's content-addressed classes, mints no class prefix, and confers no authority; its handle uses the generic artifact-handle spelling (as `intent-registry-record.record_id` and `synthesis-candidate.candidate_id` already do) and MUST NOT be in the `ev_` or `cap_` classes, which it would otherwise appear to impersonate in a `provenance.inputs` list. Every node's `provenance` takes the note's own author and `created_at`, so the compiler reads no clock (INV-005); the epoch pinning (plan §4.6) is the caller's parameter, since a compiler that quietly pinned nothing would be choosing for its caller.

**The wire: `whiteboard.compile` (W10–W12, decided at protocol 3.5 by bn-1as8e).** The previous revision recorded the wire as not decided here — "there is no `whiteboard.compile` operation and no `EvidenceQuery` field that names one" — and named the two sub-questions a wire slice would have to answer. It is decided now, as [`whiteboard.compile`](../schemas/continuumd-native-protocol.idl): the 74th operation, in a 19th namespace, at `authority propose`, with its semantics stated as `rule whiteboard.compilation`. The registry edit landed in plan §10.2, RFC 0027's authority table, and the IDL together (RFC 0026 F13's precedent, now mechanically enforced by the dossier validator's three-source parse), and the protocol minor was raised once, at the end, under `rule versioning.compatible_change`'s first trigger.

The declared surface was searched before the operation was minted, because serving already-declared vocabulary is the cheaper payment and needs no registry edit at all — the shape IDL 1.5, 1.7, and 1.8 each took. Nothing in the IDL served it. `forge.create`'s `sketch: Opaque` is RFC 0033's synthesis input and answers with a `ForgeHandle`; `context.compile` runs evidence-root-to-pack, which is the *reverse* direction and is the still-undelivered view below. So a new operation was the only honest artifact, exactly as F14 found for `evidence.link`.

- **W10 — compilation is daemon-side, and the note is what crosses.** The daemon holds the graph an entry's `references` must resolve against (W4), and holds the nodes a decision's `SUPPORTS` edges are drawn to (W6); neither is computable by a party that does not hold it, and a client resolving against a stale `evidence.query` answer would be *asserting* a fact about the graph rather than reading one — the same reason `evidence.link` names a receipt the daemon "MUST already hold" rather than accepting one. The decisive argument is what the alternative would put on the wire. A proposal carries a node kind, a claim identity, and a `provenance.actor`; a wire of *proposals* is therefore a wire of caller-filled fields, and D3's rule that a field a caller can fill is a field a caller can lie in applies to all three. W2 says an author MUST NOT be able to name the kind directly, "if it could, the seven headings would be decoration" — and only a daemon that reads the sections itself can hold that. Client-side compilation would make W2 unenforceable by construction, and would widen the untrusted surface (INV-016) from one schema-governed document to the whole twenty-member node vocabulary.
- **W11 — the note crosses as an `Opaque` naming its schema, not as a declared struct.** INV-003 makes [`whiteboard-note.schema.json`](../schemas/whiteboard-note.schema.json) normative for a note's shape, and W1 already transcribed the library from it. Declaring the same twelve-member document a second time in the IDL would create exactly the two-authority disagreement `rule conformance.registry_agreement` exists to prevent one namespace down, with no source entitled to decide it — the second authority bn-dtg61 declined for the kernels' rejection vocabularies, in a different place. The IDL's own precedent is `IntentChangeSet.changes` ("in the form of `schemas/intent-contract.schema.json`") and `context.compile`'s `pack`, and `rule encoding.opaque_payloads`'s third group is written for exactly this: a schema-governed value carried verbatim, which the codec MUST NOT re-shape. The field does not join RFC 0026 F3's four *shapeless* `Opaque` members, because it names a schema and `rule envelope.no_prose` is therefore enforceable for it. A daemon MUST validate the note against that schema **before reading any member of it**, and refuse a non-conforming note with `MalformedRequest`: INV-016 makes a note untrusted source, and a daemon that read `author` or `goal` first would be acting on a document it had not yet decided was one.
- **W12 — a note's `author` MUST be the admitted capability's actor.** This question the sub-questions did not name, and it has exactly one non-arbitrary answer. The schema requires `author`, and W9 makes every compiled node's `provenance.actor` the note's author — so a daemon that *trusted* the field would let a caller append under another principal's name, which is what `observe.ingest` and `evidence.link` both refuse by taking the actor from the admitted grant and declaring no request field for it; and a daemon that *overwrote* it would publish a compilation of a document other than the one it was handed, since a note is the caller's own artifact and its handle appears in every proposal's `provenance.inputs`. Requiring agreement is the only remaining reading, and the refusal is RFC 0027 T4's own: `CapabilityDenied`, because "an attempt to act as another principal is an authorization failure and MUST NOT be distinguishable from any other one."

The identity of a compiled node is `rule whiteboard.compilation`'s clause 4 and is D4 applied to a note: the domain tag `whiteboard-note/v1`, the kind, the subject, and the claim identity — what the node *asserts* — with the note handle, the author, and the time outside it, so two agents who write the same line about the same claim converge on one node. Its `SUPPORTS` edges take `rule evidence.edge_identity` unchanged.

**Still not decided here.** Rendering the graph back *into* a whiteboard — docs/44's "human-friendly whiteboard view" — remains undelivered: the compiler is one-way, and the view has no schema, no surface, and no decided semantics for which held nodes belong in which section. A task proposal remains a value and not an artifact: `WhiteboardTaskProposal` has a wire shape as of 3.5, but nothing publishes one, it is not a plan §4.4 class, and the graph-driven task generation docs/44 describes ("close missing proof edge", "find counterexample to candidate") is untouched — an experiment line is the only thing that becomes a task proposal today. Both belong with the six undelivered "Queries" forms below, and are carried by bn-xsuz2.
